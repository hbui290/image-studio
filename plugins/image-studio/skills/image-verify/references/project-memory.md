# Project memory and the evidence gate

`studio_state.py` keeps what a project has settled (approved deliverables, every reported defect, decisions) in a `.image-studio/` folder, and refuses to call a deliverable done until each recorded defect has a fresh crop and a verdict.

Run it as `python3 <skills>/image-verify/scripts/studio_state.py <command>` (`<skills>` is the folder that holds the skill folders). `defect add` and `gate` read images and need Pillow: if `python3 -c "import PIL"` fails, use `uv run --with pillow python3 ...`. Run the script; do not read its source. `--help` lists every command with an example. Exit codes: 0 ok (gate passed), 1 gate did not pass (or `detail-check --min-ratio` found less detail), 2 bad input or no store.

## Using the store in a skill

1. **Load once per chat.** If the session-start card is already in context, do not run `brief`; a skill handing off to another does not reload. Otherwise run `brief`.
2. **Create a store only when needed:** the user reports a defect, approves a deliverable, or asks for one. `init --project <folder> --brand <brand>` (never the home folder or inside a folder that already has a store). The first `approve deliverable --name N --file F` needs `--width W --height H --format PNG` (and `--alpha required|forbidden|any`). Record where each file came from (see "Edit chains" below): `--master` for a clean first generation or a fresh regeneration, `--from PARENT` for a file edited from deliverable PARENT.
3. **Record what the user reports:** `defect add --deliverable N --bbox x0,y0,x1,y1 --kind seam|artifact|scope|color|logo|other --note "..."`. Use `--kind scope --quote "the user's words"` for a change the user asks for that is not a mistake (new text or date, removing an element they no longer want): it needs no lesson, and the gate only checks that its box visibly changed (0.5% of pixels instead of 5%). Without the user's words it is treated like any other defect; never use it for your own mistake. A defect that covers most of the image (for example "the whole poster looks soft") is not a local repair: ask the user whether to regenerate the whole image, run image-enhance, or accept it (`defect close --status wontfix --quote "<their words>"`).
   Problems the agent finds itself (the [designer review](designer-review.md) hunt) are added with `--source agent`; `map --deliverable N --out defect-map.png` draws every open defect on one image so the user confirms them all at once.
4. **Learn from a miss after delivery.** When the deliverable had already passed the gate, `defect add` says so and marks the defect: also run `lesson add --defect D<n> --mistake "..." --cause "..." --check "..."` (what went wrong, why, and what to check next time). The gate does not pass until that lesson exists. If you delivered without a passing gate and the user rejects the result, add a lesson anyway (without `--defect` when nothing was recorded). Lessons are shared by every task (`${IMAGE_STUDIO_HOME:-~/.image-studio}/lessons.jsonl`); the session-start card and `brief` show the 5 most relevant. When `lesson add` reports that the same kind of mistake happened in 2 or more tasks, ask the user whether to make it a rule (`pref add`, with `--confirmed` only after they agree).
5. **Gate once per delivery attempt**, before telling the user it is done; not after every repair round (a repair round checks its region with `edit-check --before A --after B --bbox x0,y0,x1,y1`, which needs no store). Re-run only after a further fix. Deliver only after it exits 0.
6. **Talk to the user in plain words.** Defect IDs are internal; mention them only in parentheses. When the gate has not passed, say what is still wrong and ask what to do.
7. **Retire abandoned work.** One store keeps every job done in its folder. When the user has moved on from old deliverables (they say so, or the card's "Older work" line lists jobs they no longer want), ask, then run `retire --deliverable N [--deliverable N ...] --note "why" [--quote "their words"]`, or `retire --before YYYY-MM-DD --note "why"` for every deliverable whose last event is before that date (a UTC date, not in the future). A retired deliverable records `retired: {time, note, closed}` in `state.json`, leaves the stop hook, the session-start card and `brief`'s deliverable list, and its open defects close as `wontfix` with the note "retired: <note>" (their IDs go in `closed`). It exits 2 and changes nothing when it would close an open user complaint (any defect not `--source agent`) without `--quote` with the user's words, or when a named deliverable is current work of this chat (see [Hooks](#hooks)) without `--quote`; `--before` skips current work and names it. Retiring again keeps the first time. `retire --list` shows them; `brief` shows their count. `approve deliverable` on the same name brings one back and reopens every defect retire closed. `defect close` on a defect that is not open exits 2. An unknown name exits 2.

## Edit chains

Each edit of an edit loses a little detail; after a few rounds the image turns mushy ("nhão", "vỡ nét"). `approve deliverable` keeps the lineage so the store can see it:

- `--master` marks this file as a clean master: `root` is the deliverable itself, `chain_depth` 0, and `master` records the file's path and sha256, plus `copy`: a copy of the file kept in the store as `masters/<sha256>.<ext>`.
- `--from PARENT` says this file was edited from deliverable PARENT (give the deliverable's own name for an edit of its current file). It records `parent`, `root` (the chain's master) and `chain_depth` (PARENT's depth + 1), and carries PARENT's `master` file (PARENT's own file when it has none, copied into `masters/` while it still has its recorded sha256).
- Neither flag keeps the deliverable's existing lineage; a new deliverable starts at depth 0.

Every approval prints `Chain depth: N`; at 3 or more it also prints a warning naming the master and the `detail-check` command. Then compare, and regenerate from the master when the edit is softer:

```bash
python3 <skills>/image-verify/scripts/studio_state.py detail-check --image v9.png --master v1.png [--min-ratio R]
```

`detail-check` needs only Pillow and no store. It scales both images to the smaller short side (at most 2,048 px), so a resize does not count as lost detail. On the luminance it measures fine-band edge energy (rms of the image minus a 1 px blur) over mid-band energy (minus a 4 px blur), so a cleaner redraw with fewer strokes is not called soft. It prints `Detail: X% of master`. By default it only reports: under 93% it prints `Result: LOW` and exits 0. With `--min-ratio R` it prints `Result: FAIL` and exits 1 under R. When the two width/height ratios differ by more than 2% (another crop or layout), or the master is flat, it says "not comparable" and exits 2; compare by eye.

The 93% line is from the user's own files: edit-of-edit regenerations of one card that was later rebuilt for "accumulated redraw artifacts" scored 88-91% of its first version, earlier versions 97-99%, chains of local patches 100%, and the accepted rebuild 113% of the soft version. That is one artwork, so the check warns rather than fails. It also cannot catch softness that is already in the master: a local patch keeps the master's pixels and scores 100%.

## Taste and lessons

The goal is a designer that gets closer to the user's taste with every task. Both files are shared by every task, under `${IMAGE_STUDIO_HOME:-~/.image-studio}`, and are recorded with or without a project store. Inside a store the session-start card and `brief` show them; outside one, read them with `taste list [--brand B]` and `lesson list`.

- **Taste:** when the user approves or praises a result ("love this", "keep this one", or the same in the user's language, e.g. Vietnamese "đẹp", "giữ cái này"), record what they liked: `taste add --aspect color|line|composition|detail|lighting|text|style|other --note "what they liked, concretely" --quote "their words"` (add `--deliverable N` in a project). Notes go to `brands/<brand>/taste.jsonl` (the store's brand, or `--brand`), else `taste.jsonl`. The session-start card and `brief` show the 6 newest notes, brand and general merged, under "Your taste"; match them in the first draft.
- **Lessons:** besides a miss after delivery (step 4 above), record a method that failed twice and the one that then worked: `lesson add --mistake "..." --cause "..." --check "..." --worked "..."`.
- **Repeats and construction rules:** `defect add` records the image size each defect was reported on (`image_size`) and a 16x16 grayscale `fingerprint` of the whole image. A `--source user` defect whose box covers the region of an earlier user complaint (any status) on the same artwork is a repeat. Same artwork: the same deliverable, or another deliverable whose width/height is within 2% and whose fingerprint is close (a local repair, a rescale, or a small crop stays close; a different artwork does not; a flat, single-color image matches no other deliverable; an older record without a fingerprint uses its deliverable's current file). Same region, with boxes compared as fractions of the image: an IoU of at least 0.1; its center inside an earlier box that covers at most a quarter of the image (so a whole-image complaint does not swallow later ones); or, when the new box covers at most a quarter of the image, at least 60% of the earlier box inside it. `defect add` prints "Repeat: this region was already reported (D<n>)" and records `repeat_of`, `needs_construction`, and `needs_lesson`. Agent defects and `scope` requests with the user's words are never repeats and never count as earlier complaints. Stop patching strokes and follow [construction-reference.md](construction-reference.md), then record how the object is built: `construction add --defect D<n> --object "..." --rule "..." (--ref FILE [--ref FILE ...] | --quote "the user's words")`. Each `--ref` must be a readable image; its path (relative to the project when inside it) and sha256 are stored in the store's `construction.jsonl`. `construction list` prints every rule; the session-start card and `brief` show the 3 newest. Also run `lesson add --defect D<n>`.
- Neither changes a rule or a skill by itself. A repeated pattern becomes a rule only through `pref add --confirmed` after the user agrees.

## Brand kit

Hard facts for a brand, set with the user: `brand set --brand B --color NAME=#RRGGBB[:role] --font ROLE=Family --logo FILE --ref FILE=role --do "..." --dont "..."` (repeat flags as needed; `--remove colors:NAME|fonts:ROLE|refs:FILE|do:TEXT|dont:TEXT|logo`). It lives in `${IMAGE_STUDIO_HOME:-~/.image-studio}/brands/<brand>/brand.json` (4,000 characters at most) and records the hash of the logo and each reference. `brand show` prints it and flags a logo or reference that is missing or changed; the session-start card shows a one-line summary.

- Use the palette, fonts, and do/don't lists in the [style block](../../image-create/references/prompt-blocks.md).
- The logo is composited from that exact file, never redrawn.
- Approved references, and files the user sends in the chat, are the only existing images that may be used as style references or pixels. Never search the disk for others. Real photos found to understand how an object is built ([construction-reference.md](construction-reference.md)) are never used as pixels or style.
- Add an entry only when the user states or approves it; taste notes are for impressions, the brand kit for exact values.

## The gate

```bash
python3 <skills>/image-verify/scripts/studio_state.py approve deliverable --name N --file F   # only if the file changed
python3 <skills>/image-verify/scripts/studio_state.py defect close --id D<n> --status resolved --note "what changed"
python3 <skills>/image-verify/scripts/studio_state.py gate --deliverable N            # prints Run: <id> and Next: steps
python3 <skills>/image-verify/scripts/studio_state.py verdict --run <id> --id D<n> --status pass --evidence "what the crop shows" [--reviewer independent]
python3 <skills>/image-verify/scripts/studio_state.py verdict --run <id> --from verdicts.json   # or every verdict at once: [{"id": "D1", "status": "pass", "evidence": "..."}]
python3 <skills>/image-verify/scripts/studio_state.py gate --deliverable N --run <id>
```

Open the 100% crop of each defect first; open the 200% crop only when the 100% view is unclear. Write verdicts one call at a time (one `--from` file holds them all; parallel calls overwrite each other), and only after opening the crop; use `fail` or `uncertain` when it is not clearly fixed.

`gate` passes only when: the file's hash equals the approved one and matches the spec; every defect ever recorded on the deliverable (open and resolved, so fixed defects are re-checked) has crops in this run and no IDs are missing; no defect is open; each resolved defect has a `pass` verdict tied to this run's crop and at least 5% of its box changed since it was reported (0.5% for `scope` requests that carry the user's words); each `wontfix` carries the user's words; each defect reported after delivery (other than a `scope` request with the user's words) has a lesson; each repeat defect has a lesson and a construction rule (`construction add --defect D<n>`). A resolved defect whose pixels are identical to an earlier passing run keeps that verdict automatically ("unchanged since run ..."), so each gate only needs verdicts for regions that changed. A ZIP deliverable's spec is checked by hash and size only; a defect needs a single-image ZIP and is cropped from that image. Self-verified passes are labelled as such.

At chain depth 3 or more, `gate` also runs the detail check against the master: the store's copy, else the master file while it still has its recorded sha256 (so editing the master in place does not switch the check off). Below 93% it prints a warning under Checked: "edited N times in a chain; detail is X% of master M (path); regenerate from the master". It still passes unless you add `--min-detail R`, which turns a ratio under R into a failure. A missing or changed master, a ZIP deliverable, or images that are not comparable give a "detail check skipped" warning. Below depth 3 the check never runs.

## Preferences

`pref add [--brand B] --rule T --check T [--confirmed]` stores one-line rules in `~/.image-studio/` (per brand or general, 1,500 characters each). Without `--confirmed` it is a proposal for the user to confirm. Precedence: the user's latest instruction, then project decisions, then brand, then general preferences.

## Hooks

**Current work.** The session-start card and the stop hook look only at this chat's work. `approve deliverable`, `defect add`, `defect close`, `gate`, `verdict` and `retire` record every host session id they see (`CODEX_THREAD_ID`, `CODEX_SESSION_ID`, `CLAUDE_CODE_SESSION_ID`; Claude Code started from a Codex terminal sees two) with the time: on the deliverable (`touched`), the decision, the gate record, or the defect and its history (`sessions`, plus the first one as `session`). A deliverable is current when one of its events carries the hook's session (`session_id` in the hook input, else the host variables above), or when an event without a session id is less than 12 hours old. An event of other sessions only never makes it current. Without a valid session id in the hook, any event in the last 12 hours counts. An open defect is current when its deliverable is; when the hook has no session id at all (the host exports none), an open user defect recorded without a session id is always current until it is closed or retired; when the hook has one, such a defect is a legacy record and follows the 12-hour window like any other event without a session id. Older records written before session ids were kept count only within the 12 hours. Retired deliverables are never current. All dates and times are UTC. A defect record with a field of the wrong type (for example `history` that is not a list) makes the store read as corrupt: commands exit 2 and the stop hook blocks a completion claim until it is repaired.

- **Session start** (and after compaction) prints a short card: current open defects, current deliverables and gate status, one "Older work" line (how many older deliverables, how many have not passed the gate, and the IDs of their open defects, with the `retire` command), the 3 newest construction rules, recent decisions, the user's taste (6 newest notes), up to 5 lessons from earlier tasks, confirmed preferences. `brief` still lists every deliverable that is not retired.
  When the chat's transcript is over 25 MB, the card adds a line suggesting a new chat for a new task, since every step resends the whole history.
- **Prompt** (UserPromptSubmit) reads each user message. When it is a complaint (problem words in Vietnamese, typed with or without diacritics or as chat shorthand, such as "lỗi", "loi", "sai", "chưa đúng", "ko tự nhiên", "lệch", "méo", "gãy", "ẩu", or English "wrong", "broken", "looks off", "fix"), or an image sent with no words, and the folder has a store, it tells the agent to approve the file the user is looking at and run `defect add --source user --quote "<their words>"` before editing (never `--source agent` for the user's complaint, and [construction-reference.md](construction-reference.md) when it prints "Repeat"), and writes a pending-complaint marker (time, quote, session, turn) to the store's `pending-complaints.json`. A text-only complaint gets a marker only when it is about the image: it names something visual (an image word such as "ảnh", "card", "tay", "giáp", "logo", "màu", "viền", "image", "edge", or a deliverable's name), follows an image complaint in the same session ("k thấy sai nặng à?" after a screenshot), or comes while a user defect is open; otherwise ("fix the typo in README") it gets a one-line conditional reminder and no marker. A message ending in "mà" is a correction ("ảnh pack bài bị xé còn dính ở mép mà"). A marker counts in its own turn and the next one, then expires. `defect add` records the host's session id on the defect (`CODEX_THREAD_ID`, `CODEX_SESSION_ID`, or `CLAUDE_CODE_SESSION_ID`); a marker is satisfied only by a user defect added after it in the same session, or by one recorded without a session id. Sessions without a valid id get no marker, and their context does not promise a block. Without a store it speaks only for a complaint with a real attachment (Codex's "Image attachment: true" or `<image>` tag, not a .png name in the text), and then suggests `init` and `approve deliverable`. Only the first 4,000 characters of the user's words are classified. Blocks the host or another agent adds to a prompt (`<agent-message>`, `<task-notification>`, `<system-reminder>`, `<local-command-caveat>`, `<command-name>`, `<command-message>`, `<command-args>`, `<local-command-stdout>`, `<local-command-stderr>`; an unclosed one runs to the end) are removed first; a prompt that is only such blocks gets no context and no marker.
- **Stop** blocks only a completion claim ("done", "fixed", "ready", or Vietnamese "xong", "hoàn thành", "kiểm tra đạt", "mở bản v19", a bare "đã sửa." ending the sentence...) while a current deliverable has not passed the gate, a current defect is open, or this session's complaint was never recorded as a user defect, once per message. Older work never blocks; when the hook blocks for current work and older deliverables are unchecked, the reason adds one line with their count and the `retire` command. While a complaint is pending or a user defect is open, markdown emphasis is ignored and "đã" with an edit verb ("sửa", "chỉnh", "làm lại", "kéo dài", "bỏ", "đổi", "làm gọn", "xóa", "thêm", "nối", "vẽ lại", "cắt", "tăng", "giảm"...) anywhere in a sentence counts too ("Boss, đã sửa giáp tay và cụm card.", "Boss, đã **kéo dài** dải bạc"); only "đang", "sẽ", "tiếp", "sau đó", "chờ", "will", "next", "working on", "in progress" mark it as progress. While a complaint is pending, a reply that shows an image file (a link or path not under `refs/`) or says "mở bản / ảnh / file" counts as well. The agent then tells the user plainly what is still wrong. Questions, progress updates, and negated claims ("not done", Vietnamese "chưa xong") pass; a claim followed by a question ("Done. Anything else?") still counts. A Checked / Not checked / Still failing report passes only when it names something not checked or still failing. A session working in a separate git repo below the project folder is not policed.
- All three hooks share one command form in `hooks/hooks.json` (find `python3`, else `python`; run `studio_state.py hook <mode>`; 10-second timeout) and one output contract that both Claude Code and Codex accept: a single JSON object on stdout, or nothing. Session start and prompt print `{"hookSpecificOutput": {"hookEventName": "SessionStart" or "UserPromptSubmit", "additionalContext": "image-studio..."}}`; stop prints `{"decision": "block", "reason": "image-studio: ..."}`. They exit 0 silently when python3, the script, or a store is missing, or on any error. Codex asks the user to trust each hook once, and again whenever `hooks/hooks.json` changes (for example after an update that changes a hook's command or timeout); without hooks, record every complaint with `defect add --source user` and run `brief` and `gate` as the steps say.

Keep the store local; never ship `.image-studio/` inside a deliverable, and do not record personal data in notes.
